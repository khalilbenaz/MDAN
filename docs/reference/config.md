# Reference: configuration and runtime files

## `_mdan/<module>/config.yaml`

Every installed module gets its own `config.yaml`, written by `mdan install`/`update` and read by agents at activation. `mdan update` only ever touches the keys below — anything else you add is preserved.

### `_mdan/mdan/config.yaml` — the main config

| Key | Meaning | Source |
|-----|---------|--------|
| `project_name` | Project display name | install target folder name |
| `user_name` | Your name, used by agents in greetings and menus | `--user`, prompted, or OS user |
| `communication_language` | `français-darija` \| `français` \| `english` \| `darija` | `--lang` (`fr-darija`/`fr`/`en`/`darija`) |
| `planning_artifacts` | Where planning docs are written | `{project-root}/mdan_output/planning-artifacts` |
| `implementation_artifacts` | Where implementation docs are written | `{project-root}/mdan_output/implementation-artifacts` |
| `project_knowledge` | Where existing project docs are read from | `{project-root}/docs` |
| `project_scale` | `auto` \| `solo` \| `team` \| `enterprise` — quality-gate strictness and routing | `--scale` |

### Other modules' `config.yaml`

Optional packs (`qa`, `payments-ma`, `fintech`, `devops-azure`, `db-optimization`, `ecosystem`) get the same `user_name` / `communication_language` keys written into their own `config.yaml`; `core`'s is empty (`{}`) — it only needs the rules file, not a config.

## `_mdan/core/rules.md`

Centralizes every language and communication-style rule; every agent and wizard loads it. Changing `communication_language` in `config.yaml` is the only thing needed to change language project-wide — nothing else references a hardcoded language.

## `_mdan/state/` — runtime state (not shipped content)

| File | Written by | Contents |
|------|-----------|----------|
| `MDAN-STATE.json` | `mdan_state_update` / wizards | Current workflow + step (resume point), completed workflows, artifacts, decisions, project summary |
| `context-graph.json` | `mdan_graph_*` tools, workflow completion | The DAG: nodes (artifacts, decisions, requirements, stories, tests) and edges (`input_to`, `derived_from`, `impacts`, `references`) with file hashes for staleness |
| `export-<target>.json` | `mdan export` / `mdan_export_backlog` | Mapping from local epic/story keys to created tracker ids, for idempotent re-exports |

These are per-project runtime data, not part of the installed content — they are excluded from the npm package and from the files-manifest hash tracking (`UNHASHED` in `tools/build/build.js`).

## `_mdan/custom/` — agent customization

| File | Layer | Versioned? |
|------|-------|-----------|
| `<agent>.yaml` | team | Yes — commit it |
| `<agent>.user.yaml` | personal | No — `.gitignore`d by `_mdan/custom/.gitignore` |

Merged over the shipped template (`_mdan/_config/agents/<module>-<agent>.customize.yaml`) at load time: shipped < team < user. See [Customize an agent](../how-to/customize-agents.md).

## `_mdan/_config/` — generated manifests (do not hand-edit)

| File | Contents |
|------|----------|
| `agent-manifest.csv`, `workflow-manifest.csv`, `task-manifest.csv` | One row per agent/workflow/task, derived from the content files by `npm run build` |
| `files-manifest.csv` | Every shipped `_mdan/` file with its sha256 hash, used by `install`/`update` to detect your local edits |
| `manifest.yaml` | Installed version, modules, IDEs, install/update dates |
| `tool-manifest.csv`, `mdan-help.csv` | Standalone-task metadata used by `/mdan-help` and IDE command generation |
| `agents/*.customize.yaml` | Shipped customization templates (the "shipped" layer, see above) |

Regenerated by `npm run build`; `npm run build:check` (used in CI) fails if they're out of date.

## Project scale (`project_scale` / `--scale`)

Drives how strict `mdan check`, `mdan trace` and `mdan scope` are:

- `solo` — lightest gate, few required sections/NFRs.
- `team` — the middle ground.
- `enterprise` — strictest: more sections and NFR coverage required to pass, `mdan scope` routes more changes to full planning.
- `auto` (default) — inferred from the number of stories in the registered epics document: fewer than 5 → `solo`, 5-50 → `team`, more than 50 → `enterprise` (falls back to `team` if no epics are registered yet). Re-evaluated on every call, not fixed at install.
